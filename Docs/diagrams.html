2 · Entity reference cards

Grouped by concern. Pink = core identity. Violet = auth & access. Gold = money. Crimson = debt mechanics.

Goddess

The Dom. Owns everything downstream.
  • id uuid
  • display_name string
  • email string
  • password_hash argon2id

User (sub)

A slave. role ∈ {sub, admin}.
  • goddess_id FK
  • username unique
  • first_name, last_name
  • twitter_handle, source_note
  • status pending_entry / active / blacklisted

Invitation

Single-use token to create a sub account.
  • token uuid unique
  • entry_tribute_amount gbp
  • expires_at
  • used_at nullable

PaymentMethod

Where subs send money to the Goddess.
  • name, type Throne/PayPal/Bank/…
  • handle_or_link
  • enabled, sort_order

RollingTribute

One per sub. amount=0 ⇒ disabled.
  • amount, deadline_day, deadline_time
  • late_multiplier_per_day
  • paused
  • last_paid_at

DebtContract

Signed debt. Core entity.
  • principal, interest_rate, interest_period
  • duration_periods, payment_frequency
  • minimum_payment
  • late_penalty_severity, late_penalty_percent
  • dom_can_add_surprise_penalty
  • mid_contract_addition_mode
  • exit_amount
  • status, balance_cached
  • signed_pdf_url, signed_pdf_sha256

DebtEvent

Append-only ledger. Source of truth for balance.
  • event_type enum
  • amount, reason
  • period_index
  • created_by, created_at

DebtAdjustment

Mid-contract additions (optional sub approval).
  • amount, reason
  • status applied / pending / accepted / refused
  • proposed_by, resolved_by

PaymentDeclaration

What the sub (or Goddess) says has been paid.
  • amount, method_id
  • category entry/rolling/weekly_debt/…
  • status pending/validated/rejected/cancelled
  • external_timestamp, note

PaymentAllocation

Validated ledger line. One per declaration.
  • declaration_id FK unique
  • target_type enum
  • target_id polymorphic
  • amount

Notification

In-app notif, pushed via WebSocket.
  • user_id, type
  • payload (json)
  • created_at, read_at

BlacklistEntry

Hall of shame. Forgivable.
  • sub_id, reason
  • contract_ref_id
  • balance_at_breach
  • breached_at, forgiven_at
  • reinstatement_fee_paid

RefreshToken

JWT refresh pair.
  • user_id, hash
  • expires_at

PasswordResetToken

One-time token, 1h TTL.
  • user_id, hash
  • expires_at, used_at

3 · Debt contract state machine

One round of negotiation at most per side. The Goddess always has the last word. A never-signed contract stays in PENDING_SUB_SIGNATURE until she closes it manually.

stateDiagram-v2 [*] --> DRAFT_DOM : Goddess initiates [*] --> DRAFT_SUB : Sub initiates DRAFT_DOM --> PENDING_SUB_REVIEW : send PENDING_SUB_REVIEW --> PENDING_SUB_SIGNATURE : sub accepts as-is PENDING_SUB_REVIEW --> PENDING_DOM_COUNTER : sub counters once PENDING_DOM_COUNTER --> PENDING_SUB_SIGNATURE : Goddess accepts counter PENDING_DOM_COUNTER --> PENDING_SUB_SIGNATURE : Goddess rejects (sub keeps original) DRAFT_SUB --> PENDING_DOM_REVIEW : send PENDING_DOM_REVIEW --> PENDING_SUB_SIGNATURE : Goddess accepts PENDING_DOM_REVIEW --> PENDING_SUB_SIGNATURE : Goddess counters PENDING_SUB_SIGNATURE --> ACTIVE : sub signs (PDF) PENDING_SUB_SIGNATURE --> CANCELLED_BY_DOM : Goddess closes ACTIVE --> CLOSED : buyout validated ACTIVE --> BREACHED : Goddess marks breached ACTIVE --> COMPLETED : balance reaches 0 CLOSED --> [*] BREACHED --> [*] COMPLETED --> [*] CANCELLED_BY_DOM --> [*]
cascade Marking a contract BREACHED also transitions every other ACTIVE contract of that sub to BREACHED and the user to BLACKLISTED.

4 · Payment declaration state machine

Every tribute is declared as a single line (no split). On validation, a PaymentAllocation row is created and the target balance/counter updates.

stateDiagram-v2 [*] --> PENDING : sub declares [*] --> VALIDATED : Goddess records directly PENDING --> PENDING : sub edits (amount / method / category / note) PENDING --> CANCELLED : sub cancels PENDING --> VALIDATED : Goddess validates (may re-categorize first) PENDING --> REJECTED : Goddess rejects (optional reason) VALIDATED --> [*] : allocation emitted, counters updated REJECTED --> [*] CANCELLED --> [*]

5 · Sub account lifecycle

The status column on User drives login authorisation and UI locking.

stateDiagram-v2 [*] --> PENDING_ENTRY_TRIBUTE : signup via invitation PENDING_ENTRY_TRIBUTE --> ACTIVE : entry tribute validated PENDING_ENTRY_TRIBUTE --> DELETED : Goddess rejects / invite expired ACTIVE --> BLACKLISTED : Goddess marks breach (cascade) BLACKLISTED --> ACTIVE : Goddess forgives (records reinstatement fee) DELETED --> [*] ACTIVE --> [*]

6 · Rolling tribute cycle

A cycle runs from deadline to deadline. Paying the due amount resets it. Each extra day multiplies the amount.

stateDiagram-v2 [*] --> ON_TIME : cycle start (amount = base) ON_TIME --> PAID : sub pays in time ON_TIME --> LATE_D1 : deadline passed (+1 day) LATE_D1 --> PAID : sub pays 2x base LATE_D1 --> LATE_D2 : next day (+1) LATE_D2 --> PAID : sub pays 3x base LATE_D2 --> LATE_DN : continues (n+1)x LATE_DN --> PAID : sub pays (n+1)x base PAID --> ON_TIME : cycle reset for next week note right of LATE_DN Late multiplier is configurable per rolling (default +1 per day). late_paid triggers a notification to both sub and Goddess every morning. end note

7 · Debt event ledger flow

All balance changes on a debt contract are modelled as events. The balance is derived (or cached then recomputed on demand) from the sum of events. Events are append-only for auditability.

8 · Daily cronjob flow (08:00 Europe/London)

APScheduler embedded in FastAPI. Runs once a day. Idempotent.

10 · Porch gating (ENTRY-1)

Every request passes through the porch_gate FastAPI dependency (server/dependencies/porch_gate.py). Subs in pending_entry_tribute status are trapped on the porch: they can authenticate, read their own profile, and declare the entry tribute, nothing else. The client mirrors the check via PorchGuard at client/src/components/layout/PorchGuard.tsx, which redirects the UI to /pending-entry-tribute until the status flips to active.

flowchart TD REQ([Incoming request]) --> ALLOW{method+path on _PORCH_ALLOWLIST?} ALLOW -- "GET /auth/me" --> PASS([Pass-through]) ALLOW -- "POST /auth/login, /logout, /refresh" --> PASS ALLOW -- "POST /auth/password-reset/*" --> PASS ALLOW -- "POST /sub/payments (entry tribute)" --> PASS ALLOW -- "GET /health" --> PASS ALLOW -- no --> BEARER{Bearer header present?} BEARER -- no --> PASS_AUTH([Pass-through - normal auth will 401]) BEARER -- yes --> DECODE[Decode JWT] DECODE --> IMP{Impersonation claim?} IMP -- yes --> PASS IMP -- no --> LOAD[Load user by id] LOAD --> STATUS{user.status == pending_entry_tribute?} STATUS -- yes --> BLOCK["HTTP 403
X-Access-State: pending_entry_tribute"] STATUS -- no --> PASS BLOCK --> UI[Client PorchGuard reads header
redirect to /pending-entry-tribute]
invariant Any new route that must be reachable on the porch has to be added to _PORCH_ALLOWLIST explicitly. Silent allow-by-default is forbidden.

11 · Surprise-penalty contract picker (MONEY-1)

Goddess-only flow, reached from a sub profile via the Add penalty action. The controller filters ACTIVE contracts by dom_can_add_surprise_penalty = true before the UI decides whether to show a picker, auto-select, or disable the button. The picker modal runs in three steps: choose contract, enter amount with balance preview, confirm.

sequenceDiagram actor G as Goddess participant UI as SubProfile UI participant API as /goddess API participant DB as Database participant AUD as Audit log participant N as Notifications G->>UI: Click "Add penalty" UI->>API: GET /goddess/subs/{id}/contracts?penalty_eligible=true API-->>UI: list of ACTIVE contracts with dom_can_add_surprise_penalty=true alt 0 eligible contracts UI-->>G: Button disabled + tooltip "No contract allows surprise penalties" else 1 eligible contract UI-->>G: Auto-select, skip to amount step else 2+ eligible contracts UI-->>G: Step (a) picker modal G->>UI: Pick contract end G->>UI: Step (b) enter amount £ UI-->>G: Preview projected balance = current + amount G->>UI: Step (c) confirm UI->>API: POST /goddess/contracts/{id}/adjustments (kind=surprise_penalty) API->>DB: insert DebtEvent + update balance API->>AUD: audit entry surprise_penalty_added API->>N: notify sub API-->>UI: 201 Created UI-->>G: Toast "Penalty applied"

13 · Gender taxonomy lookup (GENDER-1)

The profile gender picker is a SearchableSelect fed by the hard-coded GENDER_TAXONOMY list (72 entries, each with value, label, and aliases[]). Filtering is a case-insensitive substring match against the label or any alias. When nothing matches, the user can write their own answer — persisted to a separate free-text field, capped at 40 characters.

14 · Audit decorator (AUDIT-1)

Every admin-console write endpoint, plus any goddess write that moves money (breach, forgive, adjustment, buyout), is wrapped in @audit_action(entity, action). The decorator captures the return value after the method succeeds and inserts an AdminAction row. On exception it does nothing — failed actions leave no trail by design, so we never log half-applied state.

sequenceDiagram actor U as Actor (admin or goddess) participant R as Router participant D as "@audit_action decorator" participant C as Controller method participant DB as Database participant AA as AdminAction table U->>R: HTTP request to write endpoint R->>D: Invoke decorated method D->>C: Run method body alt success C->>DB: Apply changes DB-->>C: Updated row C-->>D: Return Pydantic response D->>D: Capture actor_user_id, entity, entity_id, action,
payload_snapshot (serialised return value), created_at D->>AA: Insert AdminAction row D-->>R: Original result R-->>U: 2xx response else exception C-->>D: Raise D-->>R: Re-raise (no audit row written) R-->>U: 4xx / 5xx response end
scope Applied to every admin-console write endpoint, plus goddess writes that change money: breach, forgive, adjustment, surprise penalty, buyout.

15 · Realtime WebSocket envelope & heartbeat (WEBSOCKET-1)

Every frame on /ws/notifications is { type, data, ts }. Four kinds ship today: notification (existing bell payload), payment_declared (to the goddess), validation_resolved (to the sub), contract_state_change (to both parties). A 20 s server ping / 30 s pong deadline keeps half-open TCP from wedging the hub.

sequenceDiagram participant Browser participant WS as FastAPI /ws/notifications participant Hub as InProcessPublisher participant Ctrl as Controller (payment / contract) participant DB as Database Browser->>WS: Upgrade ?token=JWT WS->>WS: porch_gate short-circuits (HTTPConnection, scope != http) WS->>WS: decode JWT — close 4401 on bad token WS->>Hub: subscribe(user_id) — per-conn Queue(maxsize=32) WS-->>Browser: accept par heartbeat TaskGroup loop every 20 s WS-->>Browser: {type:"ping", ts} Browser-->>WS: {type:"pong"} end Note over WS: close code 1001 after 30 s without pong and publish loop Ctrl->>DB: write + commit Ctrl->>Hub: publish_event(user_id, "payment_declared", data) Hub-->>WS: enqueue envelope WS-->>Browser: {type, data, ts} Browser->>Browser: route: ping→pong, notification→store, else→invalidateQueries end Browser-x WS: close / network drop WS->>Hub: unsubscribe(user_id, conn)
client routing useNotificationsSocket parses the envelope, then delegates to useRealtimeInvalidations(qc) which invalidates TanStack Query via the shared queryKeys registry — never ad-hoc keys.
porch_gate fix Global app-level dep must type its scope as HTTPConnection (Starlette parent of both Request and WebSocket); previous Request typing 500ed every WS handshake because FastAPI can't build a Request from a WS scope.

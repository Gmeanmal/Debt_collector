# Writing Alembic Migrations

Migrations are the single most dangerous thing in the repo. Autogenerate is a starting point, not an answer.

## The workflow

1. Model file changes are made in `backend/models/`
2. `uv run alembic revision --autogenerate -m "<imperative message>"`
3. **Read the generated migration in full** — every line
4. Fix what autogenerate got wrong
5. Round-trip test: upgrade → downgrade → upgrade
6. Run pyright + fast tests
7. Commit

## What autogenerate gets wrong

### Partial unique indexes

Autogenerate does not detect partial indexes. You must write them as raw SQL:

```python
def upgrade() -> None:
    op.execute(
        "CREATE UNIQUE INDEX only_one_supreme "
        "ON users ((role)) WHERE role = 'supreme_leader'"
    )

def downgrade() -> None:
    op.execute("DROP INDEX only_one_supreme")
```

Known partial indexes in the project:

- `only_one_supreme` on `users` — enforces the Supreme Leader singleton
- `one_current_per_slug` on `legal_document_versions` — enforces one current version per doc slug
- `one_active_deletion_per_user` on `data_deletion_requests` — prevents double-scheduling

### Enums

Autogenerate does not handle `ALTER TYPE ... ADD VALUE` correctly. Create the enum once:

```python
def upgrade() -> None:
    op.execute("CREATE TYPE role AS ENUM ('admin', 'supreme_leader', 'goddess', 'sub', 'pending', 'banned')")
    op.create_table(
        "users",
        sa.Column("role", sa.Enum(name="role", create_type=False), nullable=False),
        # ...
    )
```

Note `create_type=False` — autogenerate will try to create the type inline per-column, which fails when multiple columns use the same enum.

Adding a value to an existing enum (one-way, no downgrade):

```python
def upgrade() -> None:
    op.execute("ALTER TYPE role ADD VALUE 'moderator'")

def downgrade() -> None:
    # PostgreSQL does not support removing enum values — documented asymmetry
    pass
```

### Foreign keys

Every FK needs explicit `ondelete=`. Autogenerate leaves it unset, which means `NO ACTION`.

```python
sa.Column("goddess_id", sa.UUID(), sa.ForeignKey("users.id", ondelete="SET NULL"), nullable=True)
sa.Column("session_id", sa.UUID(), sa.ForeignKey("sessions.id", ondelete="CASCADE"), nullable=False)
```

Rule of thumb:

- `ON DELETE SET NULL` for audit-log references (`audit_log.actor_user_id`) and for child references where the child outlives the parent (`score.goddess_id_at_time` preserves history even after the Goddess leaves)
- `ON DELETE CASCADE` only where the child is meaningless without the parent (`session_participant` → `session`)
- `ON DELETE RESTRICT` is almost never what you want — explicit error surfaces are better handled at the controller level

## Destructive operations

These require a comment + a PR body note + a reviewer's second pair of eyes:

- `op.drop_column`
- `op.drop_table`
- `op.alter_column(existing_nullable=False, nullable=True)` — tightening nullability
- `op.execute("DELETE ...")`
- `op.execute("UPDATE ... SET col = NULL")`
- Any raw SQL that mutates data

Two-phase column drops:

1. Phase 1: mark the column deprecated in the model, stop reading from it, deploy, verify logs
2. Phase 2: drop the column in a subsequent migration

Never do both phases in one migration.

## Round-trip test

Before committing, run the full cycle:

```bash
uv run alembic upgrade head
uv run alembic downgrade -1
uv run alembic upgrade head
```

If downgrade fails, fix it. Downgrades are part of the contract — a migration that cannot downgrade is a migration that cannot be reverted in a production incident.

Exception: enum value additions (documented asymmetry, leave `downgrade()` as a pass with a comment).

## Naming

- Message in imperative mood: `"add tribute_entry table"`, `"widen user description to text"`, `"add partial unique index on current legal versions"`
- File name is auto-generated hash + slug — do not rename after creation
- Revision chain must be linear — never create branching revisions unless merging feature branches

## Data migrations

Schema changes and data changes are **separate migrations**:

- Migration A: schema only (e.g. add new column)
- Migration B: data only (backfill new column from existing data)

This makes rollback predictable and keeps `upgrade()` functions small.

## Checklist before committing

- [ ] Migration message in imperative mood
- [ ] Autogenerated diff read in full
- [ ] Partial unique indexes added via raw SQL if needed
- [ ] Every FK has explicit `ondelete=`
- [ ] Enums created once, `create_type=False` on column definitions
- [ ] Upgrade → downgrade → upgrade round-trip passes
- [ ] Destructive operations flagged in the PR body
- [ ] `uv run pyright backend/` clean after migration
- [ ] `uv run pytest backend/tests/unit -q` passes after migration

## What never to do

- Never commit a migration you have not read in full
- Never skip the round-trip test
- Never drop columns without a two-phase plan
- Never run migrations against `main` in development
- Never hand-edit a migration file after it has been merged — create a new revision instead
